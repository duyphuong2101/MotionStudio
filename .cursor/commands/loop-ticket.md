# /loop-ticket — Self-healing workflow for one ticket/epic

Input: a plan slug (→ `.ai/plans/<slug>.md`), a plan file path, or a pasted AC/goal.

Run one ticket through the full workflow and **keep healing until it meets its Acceptance Criteria** — a QA or UNIT_TEST failure does NOT stop the run; it routes back to tech-lead / implementation and retries. Difference from `/workflow` + `/epic`: those hard-stop after 2 fix cycles; this escalates and continues, guarded by two safety valves.

**Step 0 — Entry gate (check FIRST every tick) + resolve AC:** read the plan file. Terminal conditions that END the loop (do NOT reschedule): `Status: done` OR all AC `- [x]` with the latest `## Verification` `@ <HEAD>` == current `git rev-parse HEAD` → DONE; `Status: blocked` OR the `## Loop Journal`'s last entry is a safety-valve STOP OR the same failure-signature in the two most recent Journal entries → BLOCKED (human must intervene). Otherwise resolve AC: plan file `## Acceptance criteria` (preferred) → Jira `getJiraIssue` if Atlassian MCP authenticated (headless usually isn't — ask to log in / paste on failure; never invent AC) → inline. If from Jira/inline, write into `.ai/plans/<slug>.md` first (durable checklist + Journal). No AC → STOP.

**Step 1 — Plan once (tech-lead):** if the plan lacks `## Scope` / `## Files`, have tech-lead produce them from the AC (+ risk tier per Step 1b: server boundary / job state / shared code → QA on; changed template look → USER_REVIEW with stills).

**Step 2 — Heal loop (repeat until DONE or a valve fires):** IMPLEMENT (`dev-quick` mechanical / `senior-dev` logic; a heal pass goes to `senior-dev-deep` (Fable 5.1) with the SPECIFIC failure + diff. **If the plan has a `## Task breakdown`, the FIRST iteration walks it task-by-task** — one task → its own `**Verify:**` → tick `- [x] done — <command> → <outcome>` → next; heal iterations do NOT re-walk it, they fix only the handed-over failure and untick any task whose Verify that fix invalidated. Task boxes are re-openable, unlike AC/Scope boxes; a net-new task tick counts as progress for the no-progress detector, an untick/re-tick of the same task does not. A partly-ticked breakdown on entry means resume at the first unticked task — that is still a first-iteration walk, not a heal) → CODE_REVIEW (the `explore` agent (.cursor/agents/explore.md, readonly) — independent, diff vs conventions + AC, NOT the implementer's context) → VERIFY (`npm test` + engine smoke, mandatory) → UNIT_TEST → QA (if risk-enabled) → CHECK AC (tick `- [x]` newly-met) → **JOURNAL** (append `<ts> | iter N | <gate> | <signature/green> | <action>` to `## Loop Journal` — the only cross-tick memory) → **COMPREHENSION EXPLAINER** (on a GREEN iteration that changed product code only — skip tests/docs/config-only: write a short prose explainer of THAT change to `.claude/state/loop-explainers/<slug>-iterN.md` — what changed & why (plain language, before code) / where (narrative, not a file list) / the one non-obvious thing a reviewer needs / reversible decisions to revisit; link its path in the Journal line. Anti-cognitive-debt: an autonomous loop out-writes what a human reads, so this trail is how a human re-enters the loop without diffing every commit — Litt, *Understanding is the New Bottleneck*). On gate failure: local bug → IMPLEMENT; structural → re-invoke tech-lead to REVISE the existing plan in place (preserve `- [x]` states, never recreate from template), then implement. Every safety-valve STOP: write Journal + `Status: blocked` + `append-outcome.js --outcome rejected` + END loop (no reschedule).

**Step 3 — DONE:** every AC checkbox `- [x]` AND VERIFY + UNIT_TEST (+ QA if on) all green in the SAME final pass. Commit on the current branch once the folder is a git repository (never push), run `node .claude/scripts/append-outcome.js --task "<slug>: <title>" --outcome accepted --verify-cycles N --plan-file .ai/plans/<slug>.md`, set plan Status: done, fill Verification — and list the run's `.claude/state/loop-explainers/<slug>-iter*.md` files there as the **understanding trail** so the human's first post-loop action is reading to understand, not diffing to reconstruct. Then **consolidate** those git-ignored per-iter explainers into a `## What the loop built` section IN the plan file (`.ai/plans/<slug>.md`, which is tracked + shared): open with ONE plain-business-language sentence (the stakeholder explainer — what it delivers for the user/business, no jargon), then 3-6 sentences of prose — shape of the change, non-obvious decisions, what a teammate must know — so the understanding reaches the team, not just your local state/ (Litt's "shared spaces"). `/release-evidence` lifts the business sentence into the PR Summary.

**Step 3b — PUBLISH:** not configured for this project (no remote, no PR tooling).

**Step 4 — Safety valves (STOP + ask):**
- Iteration cap: 8 iterations per invocation, then STOP and report — the seat and its quota are company-owned.
- No-progress: the current failure signature already appears in any of the last four Journal iterations with no new AC box and no net-new `## Task breakdown` box ticked in between → thrashing, not healing → STOP.
- Quota: `.claude/state/quota-pause.flag` at `stop` → finish the current item without spawning, journal `quota-stop`, end the tick (not blocked).
- AC unreachable without new scope / product decision / missing info → STOP.
- High-risk (server boundary, secrets, a Claude/model call shipping without review) or irreversible (dependency change, any push, out-of-scope deletion) → STOP.
- Every valve stop logs `--outcome rejected` with the reason.

Usage: `/loop-ticket quote-scene` · `/loop /loop-ticket quote-scene` (survive session boundaries) · `/loop-ticket "Goal: <AC>"`.
